# 运维经验与踩坑记录

> 记录部署、配置、Agent 管理过程中的真实教训。每一条都是踩过的坑。

---

## 1. rsync 部署：永远排除 .env

**坑**：每次 `rsync` 同步代码时，本地的 `.env.example` 或修改过的 `.env` 会覆盖服务器上的 `.env`，导致：
- `SERVER_URL` 被重置为 `http://127.0.0.1:3001`（本地值），生成的 machine reconnect 链接变成内网地址
- `OBSIDIAN_ROOT` 被错误写入服务器不存在的路径

**正确做法**：

```bash
rsync -az --exclude='node_modules' --exclude='.git' --exclude='.env' \
  backend-src/ ubuntu@82.157.4.63:/home/ubuntu/redshrimp/backend-src/
```

**关键原则**：服务器 `.env` 是服务器专属配置，永远不能被本地文件覆盖。

---

## 2. SERVER_URL：必须是公网可达地址

**坑**：`SERVER_URL=http://127.0.0.1:3001` 只对服务器自身有意义。当用户在 Machines 页面点击 "Reconnect" 时，系统会用 `SERVER_URL` 生成连接命令。如果是 `127.0.0.1`，本地机器无法连入。

**正确做法**：
- 有自定义域名：`SERVER_URL=https://shrimp.red`
- 用 Cloudflare Quick Tunnel：`SERVER_URL=https://ballot-craft-fuzzy-wet.trycloudflare.com`

**注意**：Quick Tunnel 每次重启 cloudflared 服务后地址会变，需要手动更新 `.env` 并重启后端。

---

## 3. OBSIDIAN_ROOT：不要写死在服务器 .env 里

**坑**：服务器 `.env` 里曾写了 `OBSIDIAN_ROOT=/home/jwt/JwtVault`（本地路径），导致服务器上完全找不到 vault，Memory Browser 一直报错。

**正确做法**：
- 代码里用 `resolveVaultRoot()` 函数，默认值为 `homedir()/JwtVault`
- 服务器上 `homedir()` = `/home/ubuntu`，自动对应 `/home/ubuntu/JwtVault`
- 服务器 `.env` 中**删除** `OBSIDIAN_ROOT` 一行，让代码默认值生效

```typescript
// agent-workspace.ts
export function resolveVaultRoot(): string {
  return resolve(expandHome(process.env.OBSIDIAN_ROOT?.trim() || join(homedir(), 'JwtVault')))
}
```

**原则**：有合理默认值的路径配置不应强制要求环境变量。

## 4. Agent 只能运行在安装了 claude CLI 的机器上

**坑**：在 Agents 页面创建 agent 时，若选择了服务器上的 machine（3E32），后端会尝试 `spawn('claude', ...)` 在服务器上执行，但服务器没有安装 `claude` CLI，导致 `ENOENT` 错误，agent 永远起不来。

**正确做法**：
- Agent 必须分配给**本地开发机**（安装了 `claude` CLI 的机器）
- 服务器只负责 HTTP API 和数据库，不直接运行 agent 进程
- 创建 agent 时在下拉菜单中选择本地 machine（显示为你的电脑名称，如 2CD5）

**排查方式**：看 agent 日志里是否有 `spawn claude ENOENT` 或 `spawnError`。

## 5. Nginx + certbot：证书申请后要检查配置完整性

**坑**：certbot 成功申请证书后，会自动修改 Nginx 配置，将 HTTP 80 块改为 `return 301 https://...` 并新增 443 块。但如果原来的 80 块有 `server_name shrimp.red`，certbot 重写后：
- Cloudflare Tunnel 发来的请求（Host 是 `.trycloudflare.com`）会被 Nginx 的 443 块拒绝
- 或者 80 块变成 `return 404 "No virtual host"`，导致 tunnel 完全不可用

**修复方式**：在 Nginx 配置中加一个通配 fallback 块：

```nginx
server {
    listen 80 default_server;
    server_name _;   # 接收所有 Host（包括 Cloudflare tunnel）

    root /home/ubuntu/redshrimp/frontend-src/dist;
    index index.html;

    location / { try_files $uri $uri/ /index.html; }
    location /api/ { proxy_pass http://127.0.0.1:3001; ... }
    location /socket.io/ { ... }
}
```

## 6. certbot 需要 DNS 全球生效后才能申请

**坑**：DNS A 记录添加后，DNSPod 显示"已生效"，但全球 DNS 传播需要时间（通常 5–30 分钟）。如果 certbot 在传播完成前运行，会报 `NXDOMAIN` 错误。

**正确做法**：等待 DNS 真正生效后再运行 certbot。

```bash
# 验证全球 DNS 是否生效（Google DNS）
dig +short shrimp.red @8.8.8.8
# 应返回：82.157.4.63

# 确认后再申请证书
sudo certbot --nginx -d shrimp.red -d www.shrimp.red \
  --non-interactive --agree-tos -m your@email.com
```

## 7. Vault 文件是代码生成的输出，不是人工维护的输入

**架构原则**：
- `workspace-init.ts` 里存放每个角色的初始 prompt 模板（MEMORY.md、GUIDE.md 等内容）
- Agent 首次启动时，代码自动生成这些文件到 `~/JwtVault/00_hub/agents/{agentName}/`
- vault 里的文件是**输出**，代码才是**源头**
- 不要手动编辑 vault 里的模板文件，修改要在代码里改

**好处**：重新部署时清空 vault 不会丢失任何重要配置，一切可从代码重建。

## 8. DM 频道名称：后端返回时要包含 display_name

**坑**：`POST /api/channels/dm` 原来直接返回 `channel` 行（`{ id, name: 'dm-1773679183589', type: 'dm' }`），前端没有 `display_name`，导致 DM 列表显示为时间戳 ID 而非 agent 名称。

**修复**：返回前执行 `dmWithName(id)`，通过 JOIN 查出对方的 `name` 并作为 `display_name` 返回。

**经验**：API 返回的 DM 频道对象应始终包含 `display_name`（对方的名字），前端不应自己去查。

## 9. 清空 Agent 数据的正确顺序

清空所有 agent 及其关联数据时，因为外键约束，需要按顺序删除：

```sql
DELETE FROM agent_logs;
DELETE FROM agent_runs;
DELETE FROM agents;
```

同时清空 vault 目录：

```bash
ssh ubuntu@82.157.4.63 "rm -rf /home/ubuntu/JwtVault/00_hub/agents/*"
```

## 10. 快速故障诊断清单

| 症状 | 优先检查 |
|------|---------|
| Reconnect 命令是 `127.0.0.1` | 服务器 `.env` 的 `SERVER_URL` |
| Memory Browser 显示"目录不找到" | 服务器 `.env` 里是否有错误的 `OBSIDIAN_ROOT` |
| Agent 状态一直 `error`，日志有 ENOENT | Agent 分配的 machine 是否安装了 `claude` CLI |
| Cloudflare tunnel 返回 404 | Nginx 配置被 certbot 修改，缺少 fallback `server_name _` |
| 部署后配置被重置 | rsync 命令是否加了 `--exclude='.env'` |
| certbot 报 NXDOMAIN | DNS 未全球生效，等待后重试 |
